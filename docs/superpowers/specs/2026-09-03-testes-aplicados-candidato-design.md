# Design: Gestão de testes aplicados ao candidato

Generated by brainstorming on 2026-09-03  
Repo: Prototipação Vagas (local)  
Status: APPROVED  
Mode: Builder  
Approach: 1 — Catálogo tipado + hub de aplicados + detalhe no dossiê

## Problem Statement

O protótipo precisa **padronizar a gestão dos testes aplicados** a cada candidato: listar envios com meta completa, máquina de status, ações operacionais e separação clara entre **Teste técnico**, **Comportamental** e **Avaliação por competências**.

Hoje existe catálogo de **Testes técnicos** e um bloco resumido no dossiê (`testsForCandidate` / `#candidateTests`). Falta ciclo de vida (prazo, reenvio, cancelamento, respostas, avaliação escrita, PDF, resultado) e tipos além do técnico. O portal do candidato já consome testes técnicos de forma parcial.

## Decisions

| Tema | Decisão |
|------|--------|
| Superfícies | **C** — hub operacional + dossiê completo |
| Catálogo vs aplicados | **A** — separados: catálogo = modelos; hub/dossiê = envios |
| Profundidade | **A** — ciclo completo no protótipo (inclui respostas, avaliar escritas, PDF mock, resultado) |
| Separação de tipos | **A** — abas (Técnico / Comportamental / Competências) no hub e no dossiê |
| Abordagem | **1** — catálogo tipado + hub Testes aplicados + modal de detalhe do envio |
| Persistência | Em memória no protótipo (`candidateTestAssignments` + `tests[].type`) |
| PDF | Download demonstrativo (blob/HTML), sem backend |
| Avaliação | Salvar notas das discursivas → status `Avaliado` + nota/resultado |

## Scope

### In

- Evoluir catálogo: campo `type` (`technical` \| `behavioral` \| `competency`), filtros/chips, seed com ≥1 modelo por tipo; seletor de tipo no editor técnico existente
- Nova página **Testes aplicados** em Seleção (irmã de Técnicos / Fichas)
- Dossiê do candidato → seção Testes com **3 abas de tipo**, colunas padronizadas e CTA Aplicar (modelos filtrados pela aba)
- Colunas: Teste · Tipo · Data de envio · Prazo · Status · Nota · Resultado
- Status: `Não enviado` \| `Enviado` \| `Não iniciado` \| `Em andamento` \| `Concluído` \| `Expirado` \| `Avaliado` (+ `Cancelado` via ação)
- Ações: Aplicar · Reenviar · Copiar link · Alterar prazo · Cancelar · Visualizar respostas · Avaliar questões escritas · Gerar PDF · Consultar resultado
- Modal `#candidateTestDetailDialog` (meta + Respostas / Avaliação / Resultado + ações)
- Integração leve com portal do candidato (status Não iniciado / Em andamento / Concluído quando fizer sentido no protótipo existente)
- Cache bump

### Out

- Multi-avaliador, proctoring, LMS, item bank real, estatísticas avançadas
- Editor completo novo para comportamental/competências (além de tipo + seeds; editor rico permanece o de técnico com seletor de tipo)
- Backend / persistência real

## Surfaces

1. **Catálogo** — página atual de Testes técnicos (tipada)
2. **Hub** — `#appliedTestsPage` (Testes aplicados): abas por tipo, filtros, lista, abrir detalhe
3. **Dossiê** — `#candidateTests` evoluído: abas por tipo + lista alinhada ao hub
4. **Modal** — `#candidateTestDetailDialog`
5. **Portal candidato** — reuso/extensão do fluxo de teste existente

## Data model

```text
tests[] (catálogo):
  id, title, description, type, active, minScore, questions[]

candidateTestAssignments[]:
  id: number
  candidateId: number
  vacancy: string
  jobId?: number
  testId: number
  type: "technical" | "behavioral" | "competency"
  sentAt: string | null
  dueAt: string | null
  status: "Não enviado" | "Enviado" | "Não iniciado" | "Em andamento" | "Concluído" | "Expirado" | "Avaliado" | "Cancelado"
  score: number | null
  result: string | null          // ex.: Aprovado | Reprovado | Em análise | —
  link: string
  answers: { questionId, value }[]
  writtenScores: { questionId, score?, comment? }[]
  cancelledAt?: string | null
```

- `type` no assignment espelha o tipo do modelo no momento da aplicação.
- Link demo: `https://portalrh.local/teste/{assignmentId}` (ou padrão já usado no protótipo).

## Status transitions

| Evento | Status resultante |
|--------|-------------------|
| Criar rascunho (opcional) | Não enviado |
| Aplicar / confirmar envio | Enviado (+ `sentAt`, `link`, `dueAt`) |
| Candidato abre (portal) | Não iniciado |
| Candidato inicia | Em andamento |
| Candidato entrega | Concluído (nota automática se só objetivas) |
| Prazo passou sem conclusão | Expirado |
| RH salva avaliação escrita / publica | Avaliado (`score`, `result`) |
| Cancelar | Cancelado |

## Actions matrix

| Ação | Habilitação típica |
|------|-------------------|
| Aplicar teste | Dossiê (aba) / hub |
| Reenviar | Enviado, Não iniciado, Expirado |
| Copiar link | Quando houver `link` |
| Alterar prazo | Antes de Concluído / Avaliado / Cancelado |
| Cancelar | Enquanto não Avaliado |
| Visualizar respostas | Concluído, Avaliado; Em andamento se houver parcial |
| Avaliar questões escritas | Concluído com discursivas |
| Gerar PDF | Concluído / Avaliado |
| Consultar resultado | Avaliado (ou Concluído se correção só automática) |

Clique na linha → abre `#candidateTestDetailDialog`.

## Layout notes

**Hub:** heading + abas de tipo + filtros (status, vaga, busca) + tabela/cards com colunas + empty state.

**Dossiê:** abas de tipo; CTA Aplicar abre picker de modelos daquele tipo; linhas compactas com status badge e menu ⋯ ou botões das ações frequentes.

**Modal detalhe:** header (candidato · vaga · teste · tipo · status); meta (envio, prazo, link); blocos Respostas | Avaliação | Resultado; rodapé com ações contextuais.

**Avaliação escrita:** lista só discursivas; nota + comentário; ao salvar → recalcula total → `Avaliado`.

**PDF:** blob HTML demonstrativo + download (padrão do currículo).

## Integration

- `Aplicar teste` no dossiê/hub cria `candidateTestAssignment` e alimenta o que o portal já usa (adaptar `testsForCandidate` / assigns para a nova lista canônica).
- Catálogo permanece fonte de modelos; não lista ciclo de vida.
- Agenda/entrevistas: sem mudança além de eventual link legado de teste em entrevista (fora do foco; não quebrar).
