# Design: Fluxo completo da proposta de contratação

Generated by brainstorming on 2026-09-04

Status: APPROVED (seções em chat + review do arquivo)

Approach: 2 — Modal resumo (`#offerDialog`) + editor (`#offerFormDialog`) · 1 proposta ativa + versões · resumo na Pipeline

## Problem Statement

O protótipo precisa **definir todo o fluxo da proposta de contratação**: cadastro completo (cargo, salário, benefícios, jornada, modelo, local, admissão, validade, observações), máquina de status até aceite/recusa/expiração, e ações (criar, editar, aprovar, gerar documento, enviar, reenviar, cancelar, nova versão, registrar aceite/recusa).

Hoje o modal de Proposta cobre só valor/modalidade/contrato e status simples (`enviada` / `vista` / `aceita` / `recusada`), sem aprovação RH, versões, documento nem recusa estruturada.

## Decisions

| Tema | Decisão |
|------|--------|
| Onde mora | Modal no dossiê + **resumo/chip na Pipeline** |
| Aprovação | **A** — só RH (Larissa) na mesma sessão |
| Versões | **A** — 1 ativa; nova versão arquiva a anterior |
| Gerar documento | **A** — HTML/PDF stub de visualização |
| No aceite | **A** — só registra; contratação continua manual |
| Abordagem | **2** — resumo + editor separados |

## Scope

- Expandir `#offerDialog` (resumo, status, ações, histórico/versões)
- Expandir `#offerFormDialog` com todos os campos de cadastro
- Benefícios a partir de `benefitsCatalog`
- Máquina de status completa + ações por status
- Diálogo de recusa: Motivo + Observação
- Gerar / visualizar documento (HTML stub, padrão currículo)
- Chip/resumo de status da proposta ativa no Pipeline
- `candidate.proposal` rico + `candidate.proposalVersions[]`
- Seeds + migração das propostas seed atuais
- Pendências (`proposta_aprovacao` / `retorno`) alinhadas aos novos status
- Timeline: eventos de proposta nos pontos relevantes
- Cache bump

### Out

- Página/hub Propostas na nav
- Aprovação pelo gestor / Portal do gestor
- PDF real, e-mail ou WhatsApp reais
- Contratação automática ao aceitar
- Backend
- Várias propostas ativas em paralelo

## Surfaces

1. `#offerDialog` — resumo + ações + histórico/versões + simular vista/aceite/recusa
2. `#offerFormDialog` — cadastro completo (criar/editar)
3. Diálogo de recusa (motivo + observação)
4. Pipeline — chip de status da proposta ativa no card
5. Deep-link Pendências → modal Proposta (já existente; adaptar status)

## Data model

```text
OFFER_STATUSES =
  rascunho | aguardando_aprovacao | aprovada | enviada |
  visualizada | aceita | recusada | expirada | cancelada

proposal (ativa em candidate.proposal):
  id: number
  version: number
  status: OFFER_STATUSES
  role: string                 // cargo (default = vacancy)
  salary: number               // was amount
  benefits: string[]           // from benefitsCatalog
  workSchedule: string         // jornada
  workModel: Presencial|Híbrido|Remoto
  location: string
  admissionDate: string|null   // YYYY-MM-DD
  validUntil: string|null
  notes: string
  documentGeneratedAt: string|null
  sends: [{ amount/salary, workModel, contract?, at, message?, pdf? }]
  refusalReason: string|null
  refusalNote: string|null
  approvedAt, sentAt, viewedAt, decidedAt, cancelledAt: string|null
  createdAt, updatedAt: string|null

candidate.proposalVersions: proposal[]  // arquivadas (não ativas)
```

### Compatibilidade

- Seeds atuais com `amount` / `status: enviada|vista` → migrar para `salary` + `enviada|visualizada` e preencher defaults (cargo = vaga, benefits=[], etc.).
- Manter alias de leitura `amount` → `salary` se necessário durante transição no código.

## Status machine

```text
rascunho → aguardando_aprovacao → aprovada → enviada → visualizada
                                                      ↘ aceita | recusada | expirada
cancelada ← (rascunho | aguardando_aprovacao | aprovada | enviada | visualizada)
```

- **Expirada:** ao renderizar/abrir, se `validUntil < TODAY_KEY` e status ∈ {enviada, visualizada} → `expirada`.
- **Reprovar (RH):** `aguardando_aprovacao` → `rascunho` (+ nota opcional).
- **Nova versão:** move ativa para `proposalVersions[]`; cria nova `rascunho` com version+1 (pode copiar campos).

## Actions by status

| Ação | Quando | Efeito |
|------|--------|--------|
| Criar | Sem proposta ativa | Abre editor → salva `rascunho` |
| Editar | `rascunho`; ou `aprovada` antes de enviar | Abre editor |
| Enviar p/ aprovação | `rascunho` | → `aguardando_aprovacao` |
| Aprovar | `aguardando_aprovacao` | → `aprovada` |
| Reprovar | `aguardando_aprovacao` | → `rascunho` (+ nota) |
| Gerar documento | ≥ `aprovada` | HTML stub + `documentGeneratedAt` |
| Visualizar | Doc gerado ou proposta existente | Preview HTML |
| Enviar candidato | `aprovada` | → `enviada` + `sends[]` (doc recomendado, não bloqueante) |
| Reenviar | `enviada` / `visualizada` | novo send; status `enviada` |
| Cancelar | antes de aceita/recusada/expirada | → `cancelada` |
| Nova versão | `recusada` / `expirada` / `cancelada` / `aceita` | arquiva + novo rascunho |
| Registrar aceite | `enviada` / `visualizada` | → `aceita` (sem contratar) |
| Registrar recusa | `enviada` / `visualizada` | diálogo Motivo+Obs → `recusada` |
| Simular Vista | `enviada` | → `visualizada` |

## UI notes

- Resumo: status pill, grade de campos, toolbar de ações filtrada por status.
- Editor: formulário com benefícios multi-select do catálogo ativo.
- Recusa: modal dedicado Motivo (obrigatório) + Observação.
- Pipeline: chip `Proposta · {label}` quando `candidate.proposal` existe.
- Documento: janela/HTML no estilo `openCandidateResume`.

## Error / empty states

- Sem proposta → CTA Criar no modal.
- Enviar sem campos mínimos (cargo + salário) → toast e abre editor.
- Recusa sem motivo → bloquear submit.
- Subject/candidato sumiu → toast (Pendências).

## Testing (manual)

1. Criar proposta completa → rascunho  
2. Enviar aprovação → Aprovar → Gerar doc → Visualizar  
3. Enviar candidato → Vista → Aceitar  
4. Outro fluxo: Recusar com motivo+obs → Nova versão  
5. Expirar via `validUntil` no passado  
6. Pipeline mostra chip de status  
7. Pendência de proposta abre o modal
